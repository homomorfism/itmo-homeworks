# HW2 — Воспроизведение «Deep Learning on a Data Diet»

Порт на PyTorch статьи [Deep Learning on a Data Diet: Finding Important Examples Early in
Training](https://arxiv.org/abs/2107.07075) (Paul, Ganguli, Dziugaite, NeurIPS 2021) и
воспроизведение её экспериментов на CIFAR-10 / ResNet-18 на одной RTX 3090.

Оригинальная реализация — JAX + Flax + TFDS: [mansheej/data_diet](https://github.com/mansheej/data_diet).
Здесь весь код переписан на PyTorch, окружение собирается через `uv`.

## Запуск

```bash
uv sync
uv run scripts/sanity.py                   # проверки порта + бенчмарк (нужен CUDA)
uv run scripts/sweep.py --dry_run          # план: сколько запусков и сколько это часов
uv run scripts/sweep.py --hours 11.5       # весь план (возобновляемый, по стадиям)
uv run scripts/collect.py && uv run scripts/plots.py && uv run scripts/formulas.py
```

Стадии `sweep.py` идут в порядке приоритета и каждая возобновляема: запуск, у которого уже
есть `summary.json`, пропускается, а `--hours` не даёт начать новую стадию после дедлайна.
Один процесс обучения уже полностью загружает RTX 3090 (измерено: 79 шагов/с в одиночку,
73 шага/с суммарно при 2–6 параллельных процессах), поэтому стадии выполняются
последовательно, а не параллельно.

Один запуск отдельно:

```bash
uv run scripts/run_train.py --name my/run0 --run 0 \
    --subset keep_max_scores --subset_frac 0.5 \
    --scores_path results/scores/el2n_ep20_mean10.npy
```

`sweep.py` пропускает запуски, у которых уже есть `summary.json`, поэтому его можно
останавливать и продолжать. Логи каждого запуска — в `results/logs/`.

## Что считаем

Две величины из статьи, обе — математическое ожидание по случайной инициализации весов,
оцениваемое средним по 10 независимым запускам обучения:

| | определение | где |
|---|---|---|
| **GraNd** (Def. 2.1) | $\chi_t(x,y)=\mathbb{E}_{w_t}\lVert\nabla_{w_t}\,\mathrm{CE}(p(w_t,x),y)\rVert_2$ | `scores.grand_scores` |
| **EL2N** (Def. 2.3) | $\mathbb{E}_{w_t}\lVert\mathrm{softmax}(f(w_t,x))-\mathrm{onehot}(y)\rVert_2$ | `scores.el2n_scores` |
| forgetting (Toneva et al.) | число переходов «угадал → не угадал» за всё обучение | `scores.ForgettingTracker` |

GraNd — норма градиента по **всем** 11.2 M параметров; считается через
`torch.func.vmap(grad(...))` (в оригинале — полный якобиан через `jax.jacrev`, та же
величина). Скоры считаются с BatchNorm в режиме eval и **без** аугментации — как в
оригинальном коде (`get_apply_fn_test`).

## Гиперпараметры (ровно как в `scripts/run_full_data.py` оригинала)

| | значение |
|---|---|
| сеть | ResNet-18 V1, lowres (первый свёрточный слой 3×3 /1, без max-pool) — 11 173 962 параметра |
| данные | CIFAR-10, нормализация по каналам, pad 4 (reflect) → случайный кроп 32×32 → отражение по горизонтали с p=0.5 |
| оптимизатор | SGD, momentum 0.9 **с Нестеровым**, weight decay 5e-4 на все параметры |
| lr | 0.1, умножается на 0.2 на 30 / 60 / 80 % обучения (в статье — эпохи 60/120/160 из 200) |
| батч | 128 (train), 1000 (test) |
| длительность | **число шагов = 390 × число эпох, одинаково для всех запусков** (в статье 200 эпох = 78 000 шагов) |
| сиды | `model_seed = 42 + run·424242`, `train_seed = 4242 + run·424242` (как в оригинале) |

Важная деталь оригинальной постановки, которую легко потерять: **число шагов фиксировано и
не зависит от размера подмножества**. Все скрипты оригинала (включая `run_random_subset.py` и
`run_keep_max_scores.py`) жёстко задают `num_steps = 200·390` и `decay_steps = [60,120,160]·390`,
где 390 = 50000 // 128 — число шагов в эпохе на **полном** CIFAR-10. То есть запуск на 20%
данных делает те же 78 000 обновлений, просто видит каждый пример в 5 раз чаще. Сравнение
«обрезали данные → качество не упало» в статье — это сравнение при равном бюджете шагов, а
не при равном числе проходов по данным.

## Отличия порта от оригинала

| | оригинал (JAX/Flax) | здесь (PyTorch) | почему это неважно |
|---|---|---|---|
| `'SAME'` padding при stride 2 | асимметричный (0 сверху / 1 снизу) | симметричный `padding=1` | формы совпадают, решётка сэмплирования сдвинута на 1 пиксель |
| инициализация | `lecun_normal` (flax по умолчанию) | тот же `lecun_normal` воспроизведён вручную | — |
| BatchNorm | `momentum=0.9` (flax) | `momentum=0.1` (PyTorch) | это одно и то же EMA, разные соглашения |
| точность | fp32 | bf16 autocast (мастер-веса fp32) | ускорение ровно вдвое; контрольные запуски в fp32 не выявили влияния за пределами шума по сидам (но их по одному на точку — см. отчёт, 5.9) |
| длина обучения | 200 эпох | 100 эпох (расписание lr сжато вдвое) | бюджет GPU; на полном расписании статьи эффект **сильнее** (+0.20 п.п. против +0.02), то есть отличие занижает результат — см. отчёт, 5.9 |
| окно по рейтингу (`offset`) | отсчёт от примеров с наименьшим скором | отсчёт от примеров с наибольшим скором | то же семейство окон, но параметризация совпадает с рис. 2 статьи |
| порядок примеров | датасет отсортирован по классам | исходный порядок torchvision | перестановка индексного пространства, на результат не влияет |
| детерминизм | — | `cudnn.benchmark=True` + bf16 | запуски **не** воспроизводимы побитово даже при одинаковом сиде (расхождение на 20-й эпохе ~3.5 п.п., к концу обучения — в пределах 0.19 п.п.); на оценку матожидания по инициализациям это не влияет |
| аугментация | TF на CPU | та же, но на GPU | нужна скорость: 78 000 шагов на очень маленькой сети |
| `randomize_labels` | перестановка меток внутри выбранной доли (на отсортированном массиве) | явная перестановка меток внутри выбранной доли | в оригинале это следствие индексного бага; воспроизведён смысл, а не баг |
| усреднение forgetting | `inf` у ни разу не выученных примеров попадает в среднее | `inf` заменяется на `max+1` перед усреднением | таких примеров за 200 эпох почти нет |
| чекпоинты | сохраняются каждую эпоху, скоры считаются потом | скоры считаются на месте в нужные эпохи | экономит ~9 ГБ на запуск |

## Результат

Полный разбор — в [`report/REPORT.md`](report/REPORT.md). Коротко: **98 обучений,
15.4 GPU-часа**, центральное утверждение статьи воспроизводится точно.

| | все данные | случайные 50% | EL2N 50% |
|---|---|---|---|
| 100 эпох (наш протокол) | 94.69% ± 0.19 | 92.40% | **94.71%** |
| 200 эпох (расписание статьи) | 95.14% | 93.58% | **95.34%** |

Восемь из десяти проверенных утверждений воспроизвелись; GraNd при инициализации — нет
(но тот же GraNd на 20-й эпохе работает наравне с EL2N), а оптимум скользящего окна на
чистых метках не разрешается на нашем числе запусков.

Позже добавлена кампания на **CIFAR-100** (отдельная сетка на 4×A100, 61 обучение,
29 GPU-часов, ~80 минут реального времени; см. [`report/REPORT.md`](report/REPORT.md) §5.12).
Коротко: ресайз-диета работает и на CIFAR-100, но слабее — по EL2N/forgetting можно срезать
~20–25% данных почти без потерь (76.9% база), однако при более агрессивном прунинге скоровый
отбор становится **хуже случайного**, в отличие от CIFAR-10.

```bash
uv run scripts/campaign_cifar100.py           # scores + full + prune на всех 4 GPU
uv run scripts/collect.py --runs results/cifar100/runs --out results/cifar100/summary.csv
uv run scripts/plot_cifar100.py               # results/cifar100/figures/prune_cifar100.png
```

`scripts/fleet.py` — многокарточный раннер (шардит список задач по GPU, по N процессов на
карту); на A800 одна крошечная сеть не загружает карту, поэтому выигрыш даёт упаковка
нескольких процессов (измерено: 34 → 86 шагов/с на карту при 1 → 8 процессах).
